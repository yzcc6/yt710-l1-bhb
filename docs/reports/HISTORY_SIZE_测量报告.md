# HISTORY_SIZE 测量报告（倚天 710 / Neoverse-N2）

> 实验编号：L1-1（阶段二·参数标定）
> 测量人：ZYW　　日期：2026-11-09
> 目的：**用实测确定 `HISTORY_SIZE`（BHB 分支链长度）在本平台的取值**

---

# 一、结论摘要

| 项 | 结论 |
|---|---|
| **实验用参数** | **`HISTORY_SIZE = 288`**（平台区 256~288 的代表值，重复性最好） |
| **硬件物理深度** | **≈ 64 条分支**（非本实验实测，由 Linux 内核 + USENIX Sec'25 交叉推出） |
| **两者关系** | **不是同一个量**：64 = PHR 能存多少条；288 = 灌多长最容易撞上 |
| 关键现象 | 32→288 单调上升（0.19% → 17.09%），**256~288 为平台**，320 起显著下降，336 降至 8.14% |

**一句话**：在 N2 上，把链长从上游默认的 64 提到 288，命中率从 **0.58% 提升到 17.09%（约 29 倍）**，且重复性良好（6 次标准差 0.51）。

**改动清单（共 3 处）**：

| # | 文件 | 改动 | 原因 |
|---|---|---|---|
| 1 | `common/helper.h` | `mrs pmccntr_el0` → `isb; mrs cntvct_el0`，并删除前后两次 `fence()` | PMU 不可读会 SIGILL；`fence()`（`dsb ish`）会把屏障开销计入访问延迟 |
| 2 | `common/targets.h` | 新增 `YITIAN_710` 块，`THR = 4` | 计时单位由 CPU 周期变为 20ns tick |
| 3 | **新增 `src/calib.c`** | 配对测量仪（见 3.2） | 上游「一次运行只抽 1 条训练链、无对照」导致结论不可复现 |

## 3.2 测量仪 `calib.c` 的设计

上游的缺陷：`hit_history`（训练链）在运行开始时生成**一次**，整个 run 复用 → 单次运行只回答"这一条链行不行"，运行间方差极大。

`calib.c` 的改动：

```
for hit_id in 0..HIT_NUM-1:                  # 每条训练链单独随机生成
    生成 hit_history[HISTORY_SIZE]，jit
    for round in 0..ROUNDS-1:                # 每条训练链配 ROUNDS 条触发链
        生成 ret_history[HISTORY_SIZE]，jit
        随机决定 CTRL/MAIN 顺序（记录在 order 列）
        CTRL：训练到安全目标 ftable[0] → 冲刷 → 触发 → 测 load_time，重复 ITERS 次
        MAIN：训练到攻击目标 ftable[1] → 冲刷 → 触发 → 测 load_time，重复 ITERS 次
```

**参数含义**：

| 参数 | 含义 | 本次取值 |
|---|---|---|
| `--history N` | 分支链长度（本报告的自变量） | 32 ~ 512 |
| `--hit-num M` | 不同训练链条数 | 100 |
| `--rounds R` | 每条训练链配多少条触发链 | 300 |
| `--iters K` | 每条触发链每种模式测多少次 | 100 |
| `--thr T` | 命中判定阈值（tick） | 4 |
| `--in-place 0/1` | 触发链最后一条地址是否复用训练链 | 1（主）/ 0（对照） |
| `--tail-match N` | 复用训练链尾部多少条地址 | 1（默认）/ 0 / 8 / 16 / 32 / 64 |

## 3.3 一次测量的定义（关键）

| 概念 | 定义 |
|---|---|
| **1 次测量** | 训练 → 冲刷（`dc civac` × 3）→ 触发 → 测 `load_time(fr_buf)` |
| **命中** | `load_time < THR`（4 tick = 80 ns），即 `fr_buf` 在缓存中 → 说明投机执行摸了它 |
| **1 轮** | 一条触发链 × 100 次测量 → 得到 `hits`（0~100） |
| **统计单位** | **轮**（不是次）。一轮内的 100 次共用同一条链，不独立 |

**每档规模**：100 链 × 300 轮 × 2 模式 × 100 次 = **600 万次测量 / 6 万轮**（每模式 3 万轮）。

# 五、统计分析

## 5.1 平台与斜坡

| 比较 | 差值 | t | p | 判定 |
|---|---|---|---|---|
| 256 vs 288 | 1.44 | 1.83 | ≈0.13 | **同水平（不显著）** |
| 288 vs 304 | 1.90 | 2.5 | ≈0.13 | 不显著 |
| 288 vs 320 | 6.41 | 5.8 | **<0.01** | **显著下降** |
| 256 vs 336 | 10.39 | 12.7 | **<0.001** | **高度显著** |
| 64 vs 256 | 17.95 | — | 远小于 0.001 | **高度显著（提升 29 倍）** |

**结论：256~288 构成平台，320 起进入显著下降区，336 进一步下降。**

## 5.2 重复性（方差分析）

| H | 标准差 | 与 256 的方差比 |
|---|---|---|
| 256 | 1.70 | 1（基准） |
| **288** | **0.51** | **11.3（F 检验 p<0.05，288 显著更稳）** |
| 304 | 1.28 | 1.8 |
| 320 | 1.89 | 1.2 |
| 336 | 0.54 | 9.9 |

**288 的重复性显著优于 256**：6 次运行全部落在 16.57~18.04（跨度 1.47）；
256 的 5 次跨 16.40~20.88（跨度 4.48）。

## 5.3 为什么取 288 而不是 256

| 理由 | 内容 |
|---|---|
| ① 均值无差异 | 18.53 vs 17.09，p≈0.13，说"256 更好"没有统计依据 |
| ② 288 更稳 | 方差比 11.3，p<0.05；作为基线参数，别人复现必须一致 |
| ③ 288 不在斜坡上 | 304 开始下降，288 仍处于平台内 |

# 六、对照实验（排除其他解释）

## 6.1 CTRL 对照（训练到安全目标）

在 32~256 各档，**CTRL 的 `hits ≥ 10` 轮数全部为 0**（每档 3 万轮）。
即：**"命中"只在训练到攻击目标时出现，与链长无关。**

## 6.2 原地 vs 异地（`--in-place`）

| 配置 | 测量次数 | 命中 |
|---|---|---|
| 原地（最后一条地址复用），H=256 | 600 万 | 均值 20.72 |
| **异地（最后一条也不同），H=256** | **600 万** | **0** |
| **异地，H=64** | **4,000 万** | **0** |

**合计 4600 万次异地测量，0 命中** → 效应依赖"最后一条地址复用"，不是链长本身。

## 6.3 尾部匹配数（`--tail-match`，H=256）

| tail_match | MAIN 均值 | 最大 | `≥10` |
|---|---|---|---|
| 1 | 20.36 | 61 | 25,576 |
| 8 | 16.57 | 52 | 22,227 |
| 16 | 17.86 | 55 | 23,709 |
| 32 | 18.64 | 56 | 23,797 |
| 64 | 17.05 | 64 | 23,390 |

**无单调趋势** → "匹配的历史足迹越多越容易撞"不成立。

## 6.4 顺序效应（H=64）

| 组合 | 均值 |
|---|---|
| MAIN 先跑（MA） | 0.7436 |
| MAIN 后跑（AM） | 0.5983 |
| CTRL 后跑（AM） | 0.0520 |
| CTRL 先跑（MA） | 0.0080 |

存在约 ±20% 的"顺延污染"（先跑者给后跑者留底子），故主结果为保守估计。

# 七、与文献 / 逆向数据的对比

| 来源 | 数值 | 含义 | 是否测了 N2 |
|---|---|---|---|
| **Linux 内核** `arch/arm64/kernel/proton-pack.c` | `spectre_bhb_k32`（循环 32 次） | BHB 清除循环次数 | ✅ **把 N2 归入该组** |
| **USENIX Security '25**（Zhu & Biondi） | A76 = **48**；A78AE = **64** | PHR 物理深度（= 循环次数 × 2） | ❌ **未测 N2** |
| **jia.je 逆向**（Jiajie Chen） | N2 / V1 = **64** | PHR 深度（shift-3 + 3-bit footprint） | 🟡 声称是，未独立核验 |
| **本实验** | **288** | **碰撞率最高的链长** | ✅ **本机实测** |

## 7.1 64 是怎么来的（三方交叉）

```
Linux 内核：N2 的清除循环 = 32 次（与 A78AE 同组）
论文实测  ：A78AE 的 32 次循环 → PHR = 64 条分支（规则：循环次数 × 2）
            A76   的 24 次循环 → PHR = 48 条分支（同规则，已验证）
                        ↓
              N2 的 PHR ≈ 32 × 2 = 64 条分支
```

**这个推断是可靠的**（内核为官方代码，论文为顶会实测，两者独立咬合）。
但注意：**论文的测试芯片是 A72 / A76 / A78AE，没有 N2**。所以"论文测了 N2"是误读。

## 7.2 为什么 288 ≠ 64

| 量 | 数值 | 定义 | 测量方式 |
|---|---|---|---|
| PHR 物理深度 | 64 | 硬件寄存器能存多少条分支足迹 | 逆向 / 填充循环推导 |
| **链长（本实验自变量）** | **288** | 我们灌进去的分支条数 | 直接控制 |
| 清除循环次数 | 32 | 内核冲 BHB 要跑几遍 | 官方代码 |

**三者不可互相换算。** 灌 288 条进一个只能记 64 条的寄存器，早先的会被挤出去——这正是"为什么 288 反而最好"仍未查清的原因。

## 7.3 已排除的两种解释

| 假说 | 预测 | 实测 | 判定 |
|---|---|---|---|
| 288 是 4×64 的"折叠谐波" | 320（=5×64）应出现第二峰 | 320 = 10.68，**无第二峰**，为斜坡 | ❌ 否定 |
| 碰撞 = PHR 历史足迹匹配数 | 尾部匹配 1→64 应使命中率大幅上升 | 16.6~20.4，**无趋势** | ❌ 否定 |

**机制仍未查清**，这是本报告的主要遗留问题。

# 八、结论与建议

## 8.1 参数取值

> **`HISTORY_SIZE = 288`**
> 依据：① 256 与 288 同水平（p=0.13）；② 288 重复性显著更好（σ 0.51 vs 1.70，F 检验 p<0.05）；③ 288 位于平台内、不在斜坡上。

## 8.2 给报告的表述

> "实测 `HISTORY_SIZE` 扫描（32~512，12 档）：命中率由 0.19%（H=32）单调升至 17.09%（H=288），256~288 为平台，320 起显著下降（p<0.01），336 降至 8.14%。
> 上游默认值 64 在同平台仅 0.58%，**提升约 29 倍**。
> 取 **288** 为工作点（重复性 σ=0.51，n=6）。
> 该值**不等于**硬件 PHR 物理深度；后者约 64 条，由 Linux 内核 `spectre_bhb_k32` 与 USENIX Sec'25 的 k×2 规则交叉推出。"
